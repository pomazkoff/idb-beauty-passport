## 0. Как работать с этим документом

Ты (Claude Code) строишь с нуля production-ready веб-сервис опросника для личного кабинета (ЛК) ИЛЬ ДЕ БОТЭ. Сервис:

1. показывает пользователю двухэтапный опросник (база → Паспорт красоты) ровно с той логикой и контентом, что в прототипе;
2. хранит ответы и вычисляет производные (психотип, заполненность, набор виджетов, профиль по категориям);
3. передаёт профиль во внешнюю систему **ENSI** по API через изолированный адаптер;
4. отдаёт события аналитики.

**Исходники, которые лежат в репозитории в `docs/source/`** (положи их туда до начала работы):

| Файл | Что это | Как использовать |
|---|---|---|
| `docs/source/IDB_Passport.html` | Кликабельный прототип опросника (single-file HTML) | **Единственный источник правды по контенту** (тексты вопросов, варианты, подзаголовки, тексты психотипов, виджеты, тексты экранов) и по UX-поведению. Весь контент извлекается из него программно/вручную в JSON-конфиг (раздел 6). Не копируй его код — переноси данные и поведение. |
| `docs/source/tz.rtf` (конвертирован в `docs/source/tz.md`) | Описание логики: архитектура этапов, алгоритм психотипа с проверочными случаями, таблица веток и количества вопросов, события аналитики, разметка виджетов | Источник правды по **логике и правилам**. ## 1. Цель и контекст

ЛК ИЛЬ ДЕ БОТЭ становится персонализированным. Первый шаг — короткий опросник (5 вопросов, ~1 минута), по итогам которого ЛК «собирается» под психотип пользователя (набор виджетов). Второй, опциональный шаг — «Паспорт красоты»: детальные вопросы по выбранной категории (лицо, волосы, тело, солнце, макияж, парфюмерия, парфюмерия для дома), которые дают профиль потребления для персональных рекомендаций.

Сервис — отдельный микросервис со своим API и встраиваемым фронтендом. Данные профиля должны попадать в ENSI (мастер-система клиентских данных / e-commerce платформа IDB), откуда их читают витрина, CRM и рекомендательные механики.

## 2. Границы (Scope)

### В объёме
- Фронтенд опросника: отдельная страница **и** встраиваемый виджет (один код, два режима монтирования).
- Бэкенд: REST API, хранение сессий/ответов/профилей, движок логики (ветвление, психотип, заполненность, виджеты).
- Контент опросника как версионируемый JSON-конфиг, валидируемый схемой.
- Адаптер ENSI: исходящая синхронизация профиля с гарантией доставки (outbox), опционально входящее чтение существующего профиля.
- События аналитики (клиентские + серверные).
- Админ-утилиты CLI: валидация конфига, экспорт ответов, ручной ресинк в ENSI.
- Тесты (unit, contract, e2e), Docker, CI-пайплайн, документация.

### Вне объёма (не делать, но не мешать будущему)
- Сами виджеты ЛК (ленты, календарь и т. д.) — сервис лишь отдаёт **список кодов виджетов**, которые надо показать.
- Рекомендательный движок товаров.
- Авторизация пользователей (сервис **доверяет** токену ЛК, см. 9.1).
- Админ-UI для редактирования вопросов (контент меняется через JSON + PR; UI — следующий этап, заложить расширяемость).
- Локализация (только ru-RU; но строки не хардкодить в компонентах, держать в конфиге).

## 3. Глоссарий

| Термин | Значение |
|---|---|
| **База / Этап 1** | 5 базовых вопросов: пол, 3 вопроса психотипа, категория. |

```

│ apps/web             │ HTTPS  │ apps/api (Fastify)       │        │ PostgreSQL   │
│ React, 2 режима:     │──────▶ │ REST /api/v1             │──────▶ │ sessions,    │
│ standalone / <idb-…> │        │ auth(JWT) · engine ·     │        │ answers,     │
└──────────────────────┘        │ analytics · outbox write │        │ profiles,    │
         │ dataLayer            └──────────┬───────────────┘        │ outbox,      │
         ▼                                 │ uses                   │ events       │
   Аналитика ЛК (GTM/…)                    ▼                        └──────┬───────┘
                                ┌──────────────────────────┐               │ poll
                                │ packages/core            │        ┌──────┴───────┐
                                │ чистый движок: ветвление,│        │ apps/worker  │
                                │ психотип, completeness,  │        │ outbox →     │
                                │ widgets, profile builder │        │ EnsiSink     │
                                └──────────────────────────┘        └──────┬───────┘
                                ┌──────────────────────────┐               ▼
                                │ packages/survey-config   │        ┌──────────────┐
                                │ survey.v1.json + schema  │        │ ENSI API     │
                                └──────────────────────────┘        └──────────────┘
```

**Принципы**
- `packages/core` — чистые функции без I/O; используется и фронтом (мгновенный расчёт результата), и бэком (авторитетный расчёт). Один и тот же код, одни и те же тесты.
- Сервер — источник правды: клиент может показать результат сразу, но профиль в ENSI уходит только после серверного пересчёта.
- Контент (вопросы) **не хардкодится** в компонентах: фронт рендерит любой валидный `survey.json`.
- Интеграция с ENSI изолирована за интерфейсом `EnsiSink`; бизнес-логика о ENSI не знает.

## 6. Контент опросника: формальная модель и JSON-конфиг

### 6.1 Задача
Перенести **весь** контент из `IDB_Passport.html` (объекты `T`, `L2`, `TYPES`, `W`, тексты экранов intro/result1/result2, подсказки) в `packages/survey-config/survey.v1.json`, валидируемый Zod-схемой (`survey.schema.ts`) и JSON Schema (сгенерировать для внешних потребителей).

Ключевое отличие от прототипа: прототип хранит ответы **индексами** вариантов (`S.answers[key] = i`). Это недопустимо для хранения и интеграции — при изменении порядка вариантов данные ломаются. Каждому вопросу и варианту присваивается **стабильный семантический код** (snake_case, латиница). Коды неизменны между версиями конфига; удаление варианта — через `deprecated: true`, не удалением строки.

### 6.2 Схема конфига (суть; точную Zod-схему напиши сам)

```ts
type Survey = {
  version: string;                 // semver, "1.0.0"
  locale: "ru-RU";
  genders: { code: "female"|"male"; label: string }[];   // 'ж' → female, 'м' → male
  base: Question[];                // ровно 5: gender, psycho1, psycho2, psycho3, category
  categories: Category[];          // face, body, hair, sun, makeup, perfume, home
  branches: Branch[];              // 13 штук: {gender, category, name, draft, questions: Question[]}
  psychotypes: Record<"E"|"P"|"L"|"M", { name: string; description: string }>;
  widgets: Widget[];               // 17 штук
  completeness: { basePct: 40; perCategoryPct: 20; maxCategories: 3 };
  screens: { intro: {...}; result1: {...}; result2: {...}; postponed: {...} }; // тексты экранов и кнопок
  ui: { hintSingle: string; hintMulti: string; skipLabel: string; backLabel: string; nextLabel: string; draftBadge: string };
};

type Question = {
  key: string;                     // стабильный, уникален в рамках survey: "gender", "psycho1", "face_skin_type"…
  block: string;                   // подпись этапа в прогресс-баре: "Уровень 1 · О вас" / "Паспорт · Уход за лицом"
  topic?: string;                  // «что узнаём» из RTF: "Тип кожи", "Рутина"… (для L2)
  type: "single" | "multi";
  skippable: boolean;              // в прототипе: single → false, multi → true
  draft?: boolean;                 // плашка «вопрос дописан» (ветки body/sun/makeup/perfume/home)
  text: string | { female: string; male: string };
  options: Option[] | { female: Option[]; male: Option[] };   // byGender → раздельные списки
};

type Option = {
  code: string;                    // стабильный: "oily", "t_zone", "none", "E"…
  title: string;                   // prototype `t`
  subtitle?: string;               // prototype `s` (показывается)
  vote?: "E"|"P"|"L"|"M";          // только для psycho1..3
  categoryCode?: string;           // только для вопроса category
  tags?: string[];                 // производные признаки для профиля (напр. skin_type:oily); НЕ показываются
  exclusive?: boolean;             // «Ничего не беспокоит / Не использую» — снимает остальные выборы в multi
  deprecated?: boolean;
};

type Widget = { n: number; code: string; name: string; segment: "all" | ("E"|"P"|"L")[]; why: string };
```

### 6.3 Правила переноса контента
1. Тексты переносить **посимвольно**, включая типографику («ё», длинное тире, кавычки «»). Это утверждённые маркетингом формулировки.
2. `byGender` в прототипе → `text`/`options` вида `{female, male}`. Вопросы без ветвления по полу → строка/массив.
3. Ветки `м_sun`, `м_perfume`, `м_home` в прототипе — копии женских. В конфиге не дублировать: `branch.questionsRef: "female_sun"` или общая секция `sharedBranches`. Решение зафиксируй.
4. Поле `s` в прототипе двояко: в большинстве мест это **подзаголовок** («мыло, гель, пенка»), но в `ж_face` Q1–Q2 это **диагноз** («жирная», «обезвоженная»). Перенеси его и в `subtitle` (показ как в прототипе, флаг `SHOW_TRAIT_SUBTITLE`), и в `tags` (`skin_type:oily` и т. п.) для профиля.
5. Варианты вида «Ничего не беспокоит», «Не использую…», «Ничего из перечисленного», «Пока ничего нового не хочу» → `exclusive: true`. (В прототипе этого поведения нет — это улучшение; зафиксируй в DECISIONS.)
6. Коды вариантов — короткие осмысленные английские слаги. Для psycho-вопросов код = голос (`E`/`P`/`L`/`M`). Для категории — `face|body|hair|sun|makeup|perfume|home` (как в прототипе).
7. Сгенерируй `docs/content-map.md`: таблица «ветка → вопрос (key, topic, type, число вариантов) → варианты (code → title)». Это артефакт для сверки с заказчиком.

### 6.4 Контрольные числа (должны выполняться автотестом конфига)

**Этап 1:** gender 2 варианта · psycho1 4 · psycho2 4 · psycho3 **3** (без «не подходит») · category: female **7**, male **6** (без makeup; face у мужчин называется «Уход за лицом и бритьё»).

## 7. Бизнес-логика (`packages/core`)

Все функции чистые, детерминированные, покрыты unit-тестами.

### 7.1 Ветвление
- `getBaseQuestions(survey, gender?)` — 5 вопросов; для вопросов с `{female, male}` подставляется список по полу. Пока пол не выбран (вопрос 1) — показывать только вопрос 1; остальные резолвятся после.
- `getBranch(survey, gender, category)` → ветка или `null` (например `male_makeup`).
- **Смена пола** после ответов (возврат «Назад» и выбор другого пола): сбросить ответы psycho1–3, category и все ответы Паспорта, `completedCategories = []`. Так делает прототип (`if(changed && q.key==='gender')`). Сброс — только при реальном изменении значения.

### 7.2 Психотип — `computePsychotype(votes: ("E"|"P"|"L"|"M")[]) → "E"|"P"|"L"|"M"`
Правила в порядке проверки (из RTF, совпадает с прототипом):
1. `M` встречается ≥ 2 раз → `M`.
2. Иначе считаем голоса E, P, L; максимум побеждает.
3. Максимум делят ≥ 2 типа → `M`.
4. Ни одного голоса E/P/L → `M`.

Обязательные тест-кейсы: `EEE→E`, `EEP→E`, `EPL→M`, `MME→M`, `MEE→E`, `[]→M`, `MPL→M`, `PP L→P`, `LL M→L`.
Функция принимает 0–3 голоса (вопросы могли быть не отвечены при прерванной сессии) — результат для неполного набора считать, но профиль **не** считается «база завершена», пока все 5 базовых не отвечены.

### 7.3 Заполненность — `computeCompleteness(state)`
`0`, если база не завершена; иначе `40 + 20 × min(completedCategories.length, 3)`, максимум 100. Тексты подсказки под шкалой — из `screens` конфига (три состояния: 40 %, 60–80 %, 100 %).

### 7.4 Завершение категории
Категория считается завершённой, когда пользователь прошёл последний вопрос ветки (ответил или пропустил). При `COUNT_SKIPPED_CATEGORY=true` все-пропущено тоже считается. Повторное прохождение той же категории перезаписывает ответы и **не** добавляет процент.

### 7.5 Подбор виджетов — `selectWidgets(survey, psychotype)`
- `priority` = виджеты с `segment !== "all"`, где `segment.includes(psychotype)`; для `M` — **все** неуниверсальные.
- `base` = виджеты с `segment === "all"`.
- Порядок — по `n`. Возвращать коды и полные объекты.

### 7.6 Сборка профиля — `buildProfile(survey, state) → BeautyProfile`
См. контракт в 10.2. Включает: пол, психотип (+ разбивку голосов), первичную категорию, завершённые категории, заполненность, виджеты, нормализованные ответы (`question_key → option_codes[]`, `skipped`), агрегированные `traits` (из `tags` выбранных вариантов), `survey_version`, `profile_revision` (монотонный счётчик на пользователя).

### 7.7 Валидация ответа — `validateAnswer(question, optionCodes[])`
- `single`: ровно 1 код, из списка допустимых для пола.
- `multi`: 0..N кодов (0 только если `skippable`); при наличии `exclusive`-варианта — либо он один, либо без него.
- Неизвестный/`deprecated` код → ошибка 422 с указанием кода.

## 8. Фронтенд

### 8.1 Режимы монтирования
- **Standalone**: `/` (и `/?customer_token=…` для отладки), полноэкранная страница как в прототипе.
- **Embed**: web-компонент `<idb-beauty-quiz api-base="…" token="…" theme="light">`, бандл `embed.js` (ESM + IIFE), Shadow DOM, CSS-переменные для темизации из прототипа (`--brand:#E30138` и др.). События наружу: `quiz:base-completed`, `quiz:category-completed`, `quiz:closed` (CustomEvent с профилем в `detail`), чтобы ЛК мог перестроить виджеты без перезагрузки.

### 8.2 Экраны (1:1 с прототипом по структуре и текстам)
1. **Intro** — заголовок, лид, карточка «Что вы получите сразу», кнопка «Начать». Если у пользователя уже есть профиль — вместо Intro сразу **Result** (с кнопкой «Пройти заново» и «Дополнить Паспорт»).
2. **Question** — прогресс-бар (`step/total`), подпись блока, текст, подсказка «Выберите один вариант / Можно выбрать несколько», варианты (радио/чекбокс стилизованные как карточки), плашка «вопрос дописан» для `draft`. Навигация: single — переход по клику на вариант; multi — «Далее» (disabled при 0 выбранных) и «Пропустить»; «Назад» со 2-го вопроса. Скролл вверх при смене вопроса.
3. **Result 1** (после базы) — шкала заполненности, карточка психотипа, приоритетные и базовые виджеты, анонс Паспорта с кнопкой «Собрать Паспорт · {категория}» и «Позже» (→ блок «Хорошо, вернёмся к этому позже» + «Всё-таки собрать»), пояснение «Как считается тип», «Пройти заново».
4. **Result 2** (после категории) — шкала, психотип, таблицы «Паспорт · {категория}» по всем завершённым категориям (topic → выбранные варианты через « · », подзаголовок в скобках), виджеты, блок «Добавьте ещё категорию» со списком незавершённых категорий (для данного пола), «Пройти заново».

### 8.3 Состояние и восстановление
- Состояние сессии хранится на сервере; клиент при монтировании делает `GET /api/v1/me/session` и продолжает с места остановки (этап, индекс вопроса). Локально — только оптимистичный кэш (`sessionStorage`), не источник правды.
- Каждый ответ отправляется немедленно (`PUT …/answers/{questionKey}`); при сетевой ошибке — повтор с экспоненциальной задержкой, UI не блокируется, показывается ненавязчивый индикатор «сохраняем…».
- «Пройти заново» → `POST /sessions/reset` (старый профиль архивируется, в ENSI уходит новый снапшот после завершения базы).

### 8.4 Качество UI
- Доступность: фокус-кольца, роли `radiogroup`/`group`, `aria-checked`, навигация с клавиатуры (стрелки/пробел/Enter), контраст AA, `prefers-reduced-motion`.
- Производительность: embed-бандл ≤ 60 KB gzip без шрифтов; шрифты (Cormorant Garamond, Manrope) подключать через `font-display: swap`, в embed-режиме наследовать шрифты хоста, если задан атрибут `inherit-fonts`.
- Адаптив от 320 px; таблица профиля на мобильном в одну колонку (как в прототипе `@media(max-width:520px)`).
- Никаких `alert/confirm`. Ошибки — инлайн.

## 9. API сервиса (`apps/api`)

Префикс `/api/v1`. Конверт ответа — как в ENSI, для единообразия экосистемы: `{ "data": …, "meta"?: …, "errors"?: [{code, message, meta?}] }`. OpenAPI 3.1 генерируется из Zod-схем и публикуется на `/api/v1/openapi.json` + Swagger UI на `/docs` (только вне production или за флагом).

### 9.1 Аутентификация
- `Authorization: Bearer <JWT>` от ЛК. Проверка подписи (JWKS URL или PEM из env), `iss`, `aud`, `exp`. `sub` → `customer_id` (строка; формат не интерпретировать).
- Dev-режим (`AUTH_MODE=dev`): заголовок `X-Customer-Id`. В production запрещён на уровне конфига (сервис не стартует).
- Все эндпоинты, кроме `/health`, `/survey`, `/openapi.json`, требуют аутентификации. Пользователь видит только свои данные.

### 9.2 Эндпоинты

| Метод и путь | Назначение |
|---|---|
| `GET /survey?gender=female\|male` | Текущая версия конфига, уже отфильтрованная по полу (если пол передан); без пола — только базовый вопрос `gender` + метаданные. Кэш `ETag`. |
| `GET /me/session` | Текущая сессия: `{ sessionId, surveyVersion, stage, currentQuestionKey, answers, derived: { psychotype, completenessPct, completedCategories, widgets } }`. Если сессии нет — создаётся пустая. |
| `PUT /me/session/answers/{questionKey}` | Тело `{ optionCodes: string[], skipped: boolean, timeMs?: number }`. Валидация 7.7. Возвращает обновлённую сессию + `derived`. При смене пола применяет сброс 7.1. |
| `POST /me/session/base:complete` | Фиксирует завершение базы (сервер проверяет, что все 5 ответов есть). Пересчитывает профиль, пишет `profiles` revision, кладёт задание в outbox. Возвращает `BeautyProfile`. |
| `POST /me/session/passport:start` | Тело `{ category }`. Проверяет, что ветка существует для пола. |
| `POST /me/session/passport:complete` | Тело `{ category }`. Проверяет, что все вопросы ветки отвечены/пропущены. Добавляет категорию в завершённые, пересчитывает, outbox. Возвращает `BeautyProfile`. |
| `POST /me/session:reset` | Архивирует сессию и профиль, создаёт новую. |
| `GET /me/profile` | Последний `BeautyProfile` (то, что ушло/уйдёт в ENSI) + статус синхронизации `{ ensi: { status: pending\|sent\|failed, lastAttemptAt, revision } }`. |
| `POST /events` | Пакет аналитических событий `{ events: [{ name, params, ts }] }` (см. 11). |
| `GET /health`, `GET /ready`, `GET /metrics` | Служебные. |

Коды ошибок (`errors[].code`): `UNAUTHORIZED`, `FORBIDDEN`, `VALIDATION_ERROR`, `QUESTION_NOT_FOUND`, `OPTION_NOT_ALLOWED`, `STAGE_NOT_COMPLETE`, `BRANCH_NOT_AVAILABLE`, `SURVEY_VERSION_MISMATCH`, `RATE_LIMITED`, `INTERNAL`.

### 9.3 Хранение (Prisma, PostgreSQL)

- `survey_versions(version PK, config JSONB, checksum, published_at)` — конфиг загружается при старте из пакета, регистрируется здесь; сессия всегда привязана к версии, с которой началась.
- `sessions(id, customer_id, survey_version, status: active|archived, gender, stage, current_question_key, started_at, updated_at, archived_at)` — индекс `(customer_id, status)` с уникальностью одной активной сессии.
- `answers(session_id, question_key, option_codes TEXT[], skipped, time_ms, answered_at)` — PK `(session_id, question_key)`.
- `profiles(id, customer_id, session_id, revision, payload JSONB, created_at)` — снапшот `BeautyProfile`; `UNIQUE(customer_id, revision)`.
- `ensi_outbox(id, profile_id, customer_id, revision, status: pending|sending|sent|failed|dead, attempts, next_attempt_at, last_error, created_at, sent_at)`.
- `analytics_events(id, customer_id, session_id, name, params JSONB, client_ts, server_ts)`.

Персональные данные: хранить только `customer_id` (идентификатор ЛК) и ответы. Никаких имён/email/телефонов. Ретеншн: архивные сессии и события старше N дней (env, по умолчанию 365) удаляются джобой.

## 10. Интеграция с ENSI

### 10.1 Что известно и что нет
Известно (из открытой документации ensi.tech): REST, версия в URL (`/api/v1/...`), ресурсы во множественном числе kebab-case, конверт `{data, meta, errors}`, поиск через `POST <resource>:search` с `filter/sort/include/pagination`, ошибки `{code, message, meta}`, трейсинг через заголовки. ENSI поставляет OpenAPI-контракты на каждый сервис и генератор клиентов.

**Неизвестно и должно быть предоставлено командой IDB/ENSI** (до этого — моки): точный сервис и эндпоинт для записи профиля клиента (вероятно, сервис Customers или кастомный сервис/поле атрибутов), схема авторизации сервис-сервис (токен/заголовок), идентификатор клиента на стороне ENSI (совпадает ли с `sub` из JWT ЛК или нужен маппинг), нужен ли обратный поток (чтение профиля из ENSI).

**Не придумывай пути ENSI.** Положи реальный OpenAPI-файл в `packages/ensi-client/openapi/ensi.yaml`, когда он появится, и сгенерируй типизированный клиент (`openapi-typescript` + `openapi-fetch`). До этого реализуй `EnsiSink` с тремя реализациями.

### 10.2 Контракт исходящего профиля — `BeautyProfile` (наш, стабильный; маппинг на поля ENSI — отдельный слой)

```json
{
  "schema_version": "1.0",
  "customer_id": "string",
  "profile_revision": 3,
  "survey_version": "1.0.0",
  "updated_at": "2026-10-06T07:30:00Z",
  "gender": "female",
  "psychotype": { "code": "E", "name": "Эмоциональный", "votes": { "E": 2, "P": 1, "L": 0, "M": 0 } },
  "primary_category": "face",
  "completed_categories": ["face", "hair"],
  "completeness_pct": 80,
  "widgets": { "priority": ["news_blog", "beauty_services", "recommendations_feed", "community", "gamification", "closed_sales", "beauty_boxes"],
               "base": ["favorites", "preferences_quiz", "loyalty", "wishlist", "notifications", "order_info"] },
  "answers": [
    { "stage": "base", "question_key": "psycho1", "option_codes": ["E"], "skipped": false, "answered_at": "…" },
    { "stage": "passport", "category": "face", "question_key": "face_skin_type", "option_codes": ["combination"], "skipped": false, "answered_at": "…" }
  ],
  "traits": { "face.skin_type": ["combination"], "face.concerns": ["dehydrated", "dull"], "hair.wash_frequency": ["every_other_day"] }
}
```

`traits` — плоский словарь `"<category>.<topic_slug>" → codes[]`, собранный из `tags`/кодов выбранных вариантов. Это то, что удобно класть в атрибуты клиента в ENSI и использовать в сегментации.

### 10.3 Механика доставки (outbox)
1. При `base:complete` / `passport:complete` в **одной транзакции** с записью `profiles` создаётся запись `ensi_outbox(status=pending)`.
2. `apps/worker` опрашивает outbox (`FOR UPDATE SKIP LOCKED`), берёт пачку, вызывает `EnsiSink.upsertProfile(profile)`.
3. Идемпотентность: заголовок `Idempotency-Key: <customer_id>:<revision>` (если ENSI поддерживает) и проверка на нашей стороне, что ревизия не отправлялась. Отправляется **всегда последняя** ревизия клиента; более старые pending-записи того же клиента помечаются `superseded`.
4. Повторы: экспоненциальная задержка 1 мин → 2 → 4 … до 24 ч, максимум 10 попыток, затем `dead` + алерт (лог уровня error + метрика `ensi_outbox_dead_total`). Повторять только на 5xx/сетевых ошибках и 429; на 4xx (кроме 429) — сразу `failed` с сохранением тела ответа.
5. CLI `pnpm ensi:resync --customer <id> | --all --since <date>` — ручной ресинк.
6. Статус синка виден в `GET /me/profile` и в метриках.

### 10.4 Интерфейс адаптера
```ts
interface EnsiSink {
  upsertProfile(profile: BeautyProfile, ctx: { traceId: string; idempotencyKey: string }): Promise<{ externalId?: string }>;
  fetchProfile?(customerId: string): Promise<BeautyProfile | null>;   // опционально, для входящего потока
}
```
Реализации: `MockEnsiSink` (в памяти, для тестов), `FileEnsiSink` (пишет JSON в `./.ensi-out/`, для локальной демонстрации), `HttpEnsiSink` (реальный, на сгенерированном клиенте; маппинг `BeautyProfile → ENSI payload` в отдельном модуле `mapping.ts` с собственными тестами). Выбор — env `ENSI_SINK=mock|file|http`.

Все вызовы ENSI логируются (без тела ответа в production, с `traceId`, длительностью, статусом). Таймаут запроса 10 с. Прокидывать `traceparent`.

## 12. Нефункциональные требования

- **Безопасность:** CORS только с доменов ЛК (env), rate limit на `/events` и `/answers` (например, 60 req/мин на пользователя), `helmet`-заголовки, CSP для standalone. Секреты — только через env; `.env.example` без значений.
- **Надёжность:** API stateless, горизонтально масштабируется; воркер — один инстанс или несколько с `SKIP LOCKED`. Graceful shutdown.
- **Наблюдаемость:** структурированные логи с `traceId`, `customerId` (хэшированный в логах), метрики: латентность эндпоинтов, число завершённых баз/категорий, размер outbox по статусам, попытки/ошибки ENSI.
- **Производительность:** p95 ответа API < 150 мс без учёта сети; `GET /survey` отдаётся из памяти с ETag.
- **Совместимость:** браузеры последних 2 версий + iOS Safari 15+; WebView приложения ИДБ.
- **Данные:** все миграции — через Prisma Migrate, обратимые. Сид-скрипт с демо-пользователем и тремя сценариями (E, P, M).

## 13. Тестирование

1. **Валидация конфига** (`packages/survey-config`): схема проходит; контрольные числа из 6.4 **для каждой ветки и каждого вопроса** (topic, type, число вариантов); уникальность всех `key` и `code`; у psycho-вопросов каждая опция имеет `vote`; psycho3 не содержит `M`; `male` не имеет `makeup`; текст каждой опции непустой и не содержит «ё→е» потерь (сравнение с прототипом через извлечённый снапшот `docs/source/prototype-content.snapshot.json`, который ты получаешь скриптом из HTML).
2. **Движок** (`packages/core`): психотип (кейсы 7.2), заполненность (0/40/60/80/100, повтор категории не добавляет), виджеты (точные множества для E/P/L/M и порядок), сброс при смене пола, валидация ответов, сборка профиля (снапшот-тест JSON).
3. **API** (contract): каждый эндпоинт — успех + все ошибки; изоляция пользователей; одна активная сессия; транзакционность `complete` + outbox.
4. **Worker/ENSI:** retry-политика, superseded, dead-letter, идемпотентность — с `MockEnsiSink`, а также с `msw`/nock-заглушкой HTTP под конверт ENSI `{data, errors}`.
5. **E2E (Playwright):** 4 сценария — женщина E (лицо → волосы), мужчина P (лицо и бритьё), смешанный M (все виджеты), прерывание и восстановление сессии; смена пола со сбросом; «Позже» → «Всё-таки собрать»; проверка `dataLayer`-событий по списку 11.
6. **Доступность:** axe-core в e2e без критических нарушений.
7. CI: lint, typecheck, unit, contract, e2e (в Docker), сборка образов. Покрытие `packages/core` ≥ 95 %.

## 15. Расхождения источников и принятые решения (применять без уточнений)

| # | Расхождение | Решение |
|---|---|---|
| 1 | В RTF таблица «Разметка виджетов» содержит 15 строк, а текст RTF и прототип говорят о **17** (в таблице пропущены «Общение с комьюнити» (E) и «Геймификация» (E)); нумерация после №8 сдвинута. Подсчёты RTF (E: 7 приоритетных) сходятся только с 17 виджетами прототипа. | Источник правды — массив `W` прототипа (17 виджетов, его нумерация). Зафиксировать в DECISIONS, пометить в content-map. |

| 4 | Пропуск всех multi-вопросов категории всё равно даёт +20 %. | Сохраняем (`COUNT_SKIPPED_CATEGORY=true`), флаг в конфиге. |
| 5 | Поле `s` у части вариантов — диагноз, у части — подзаголовок. | И показывать (как прототип), и писать в `tags`. Флаг `SHOW_TRAIT_SUBTITLE`. |
| 6 | Ветки body/sun/makeup/perfume/home помечены как «дописанные ИИ, могут поменяться». | `draft: true` в конфиге, плашка в UI; контент меняется только правкой JSON + bump версии. Старые сессии продолжают работать на своей версии. |
| 7 | В прототипе нет взаимоисключающих вариантов («Ничего не беспокоит» можно выбрать вместе с проблемами). | Ввести `exclusive: true` (улучшение данных). Пометить в DECISIONS как отклонение от прототипа. |
| 8 | В прототипе категория из вопроса 5 не зависит от пола по кодам, но мужской список короче. | Коды общие; доступность ветки проверяется `getBranch`. |
| 9 | Мужские ветки sun/perfume/home = женские. | Не дублировать контент (ссылка). |
| 10 | Прототип не хранит ничего между перезагрузками. | Серверная сессия и восстановление (8.3). |

**Открытые вопросы, которые НЕ блокируют разработку** (работаем на моках, фиксируем в `docs/ENSI.md` и `docs/DECISIONS.md`):
- Точный эндпоинт/сервис ENSI, схема авторизации, идентификатор клиента, нужен ли обратный поток.
- Формат JWT ЛК (issuer, JWKS URL, имя клейма с id клиента).
- Домен(ы) ЛК для CORS и способ встраивания (iframe vs web-component).
- Нужно ли показывать `draft`-плашку в production (по умолчанию: показывать только при `SHOW_DRAFT_BADGE=true`, в production — выключено).

## 16. Этапы работ (выполнять последовательно; каждый — с тестами и записью в DECISIONS)

1. **Каркас.** Монорепо, линт/форматирование, CI, Docker Compose с Postgres, `README`. Пустые приложения стартуют, `/health` отвечает.
2. **Извлечение контента.** Скрипт `scripts/extract-prototype.ts`: парсит `docs/source/IDB_Passport.html` (вытаскивает `T`, `L2`, `TYPES`, `W`, тексты экранов) → `prototype-content.snapshot.json`. Ручная сборка `survey.v1.json` с кодами; Zod-схема; тесты контрольных чисел (6.4) зелёные; `content-map.md` сгенерирован.
3. **Движок `core`.** Все функции раздела 7 + тесты, покрытие ≥ 95 %.
4. **API + БД.** Prisma-схема, миграции, эндпоинты 9.2, auth (jwt + dev), OpenAPI, contract-тесты.
5. **Фронтенд.** Standalone-режим 1:1 с прототипом по экранам и текстам; восстановление сессии; аналитика в `dataLayer` + `/events`. Затем embed-сборка web-компонента и события наружу.
6. **ENSI-адаптер и воркер.** Outbox, retry, superseded, dead-letter, `Mock`/`File`/`Http` sink, mapping с тестами, CLI ресинка, `docs/ENSI.md` с перечнем того, что нужно получить от команды ENSI, и инструкцией подключения контракта.
7. **E2E, доступность, полировка.** Playwright-сценарии, axe, производительность бандла, RUNBOOK. Финальная сверка `content-map.md` с прототипом.
