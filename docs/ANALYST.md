## 1. Границы задачи

Сервис считает двухэтапный опросник «Паспорт красоты» и хранит один профиль на клиента.

Интеграция личного кабинета — только по API. Фронт ЛК сам рисует вопросы и вызывает методы сервиса с JWT пользователя.

Вне объёма сервиса:

- выпуск токенов и учётные записи пользователей (это backend ЛК);
- приём профиля на стороне ENSI (контракт принадлежит ENSI);
- виджеты витрины ЛК (сервис отдаёт только их коды).

Без токена пользователя методы сессии не открываются. Анонимного входа нет.

## Как можно получить web-компонент и репозиторий с бэковой частью кода?

Web-компонент в поставку не входит. Интеграция только по API.

Бэкенд и весь код сервиса лежат в этом репозитории: [pomazkoff/idb-beauty-passport](https://github.com/pomazkoff/idb-beauty-passport). Доступ выдаётся команде ИЛЬ ДЕ БОТЭ на GitHub. Репозиторий передаётся, когда аналитик принимает сервис. Сервис разворачивается в инфраструктуре ИЛЬ ДЕ БОТЭ.

## 2. Роли

| Роль | Что делает |
|---|---|
| Покупатель | Проходит опросник в личном кабинете |
| Фронт ЛК | Рисует экраны и вызывает API |
| Продакт | Публикует версии опросника в конструкторе |
| ENSI | Хранит профиль клиента. Контракт приёма — у команды ENSI |
| Backend ЛК | Выпускает JWT пользователя |

Роли «Эксплуатация» нет. `GET /api/v1/health`, `GET /api/v1/ready` и `GET /metrics` — служебные методы процесса для оркестратора и Prometheus, не роль и не контур интеграции.

## 3. Направление вызовов

| Вызов | Направление |
|---|---|
| `GET /survey`, сессия, ответы, завершения, `GET /me/profile`, `POST /events` | фронт ЛК → API опросника |
| `fetchProfile` на пустом входе | API опросника → ENSI |
| Push профиля | воркер опросника → ENSI |
| `GET /api/v1/integration/...` | система с ключом `X-Api-Key` → API опросника |
| Конструктор | `apps/admin` → API, заголовок `X-Admin-Token` |

Методы сессии вызывает фронт ЛК. Это не вызовы ENSI к опроснику.

## 4. Авторизация пользователя

Сервис принимает только токены авторизации пользователей ИЛЬ ДЕ БОТЭ. Своих пользователей не заводит и токен не подписывает.

Проверка (`AUTH_MODE=jwt`):

1. Заголовок `Authorization: Bearer <jwt>`.
2. Подпись RS256: JWKS (`JWT_JWKS_URL`) или PEM (`JWT_PUBLIC_KEY_PEM`, алгоритм RS256).
3. `iss` = `JWT_ISSUER`, `aud` = `JWT_AUDIENCE`, срок `exp`.
4. Id клиента из клейма `JWT_CUSTOMER_CLAIM` (если имя не задано — `sub`). Значение — строка или число.

Подтверждено: этот id равен id клиента в ENSI. Отдельного сопоставления нет.

`X-Admin-Token` фронт ЛК не передаёт. На `GET /api/v1/me/session` он нужен только вместе с query `version` (предпросмотр черновика конструктора). Без `version` достаточно JWT пользователя. Иначе предпросмотр отвечает 403.

`X-Customer-Id` и `?customer=` — только стенд `AUTH_MODE=dev`. В `NODE_ENV=production` этот режим не стартует и в OpenAPI не объявлен.

## 5. Ход пользователя

1. Фронт запрашивает `GET /api/v1/survey` и `GET /api/v1/me/session`.
2. Пустой вход читает профиль из ENSI. Если он собран, сессия открывается на результате. Если профиля нет или ENSI недоступен, опросник начинается с `intro`, HTTP 200.
3. Пользователь отвечает. Каждый ответ — `PUT /api/v1/me/session/answers/{questionKey}`.
4. Конец базы — `POST /api/v1/me/session/base:complete`. Воркер отправляет профиль в ENSI.
5. Категория Паспорта — `passport:start`, ответы, `passport:complete`. Каждое завершение категории снова обновляет тот же профиль и ставит доставку.
6. «Пройти заново» — `POST /api/v1/me/session:reset`. Сессия пустая, профиль не удаляется и в ENSI не уходит. Следующее завершение обновляет ту же запись.
7. Коды виджетов ЛК фронт читает из профиля: `widgets.priority` и `widgets.base`.

Диаграмма — в [`INTEGRATION.md`](INTEGRATION.md).

## 6. Зачем хранить опросник

Текст живёт в таблице `survey_versions`, а не в выкладке фронта.

- Продакт публикует новую версию из конструктора без деплоя кода.
- Опубликованная версия одна. Предыдущая становится архивной.
- Сессия дочитывается на версии, на которой начата. `SURVEY_VERSION_MISMATCH` (409) возникает, только если эту версию удалили.
- Фронт ЛК забирает опубликованный конфиг под один пол: `GET /api/v1/survey`.
- Другая система забирает полный документ (оба пола, голоса, теги): `GET /api/v1/integration/surveys/current`.

`packages/survey-config/survey.v1.json` — сид первой версии и фикстура тестов, не рантайм-источник.

## 7. Объект ответов

Тело `PUT /api/v1/me/session/answers/{questionKey}`:

```json
{ "optionCodes": ["female"], "skipped": false, "timeMs": 1200 }
```

В сессии `data.answers` — объект. Ключ равен `question_key`. Значение:

| Поле | Тип | Смысл |
|---|---|---|
| `optionCodes` | массив строк | коды вариантов; пустой массив только при `skipped: true` |
| `skipped` | boolean | вопрос пропущен |
| `timeMs` | необязательное целое | миллисекунды на экране |
| `answeredAt` | строка ISO-8601 | момент сохранения на сервере |

В OpenAPI эта форма задана схемой, не пустым объектом.

Пример фрагмента сессии:

```json
{
  "answers": {
    "gender": {
      "optionCodes": ["female"],
      "skipped": false,
      "timeMs": 1200,
      "answeredAt": "2026-10-08T12:00:00.000Z"
    }
  }
}
```

В профиле те же ответы лежат массивом `answers[]`: `stage`, `category` (необязательно), `question_key`, `option_codes`, `skipped`, `answered_at` (необязательно).

## 8. Профиль: все поля

`BeautyProfile`:

| Поле | Тип |
|---|---|
| `schema_version` | строка `1.0` |
| `customer_id` | строка |
| `profile_revision` | целое |
| `survey_version` | строка |
| `updated_at` | строка ISO-8601 |
| `gender` | `female` или `male` |
| `psychotype.code` | `E`, `P`, `L` или `M` |
| `psychotype.name` | строка |
| `psychotype.votes.E` | число |
| `psychotype.votes.P` | число |
| `psychotype.votes.L` | число |
| `psychotype.votes.M` | число |
| `primary_category` | код категории или `null` |
| `completed_categories` | массив кодов |
| `completeness_pct` | число |
| `widgets.priority` | массив кодов виджетов ЛК |
| `widgets.base` | массив кодов виджетов ЛК |
| `answers` | массив, форма в разделе 7 |
| `traits` | объект, ключ `категория.тема`, значение — массив кодов |
| `tags` | массив строк |

Психотипы опубликованного сида: E «Эмоциональный», P «Прагматичный», L «Премиальный», M «Смешанный». Категории Паспорта: `face`, `body`, `hair`, `sun`, `makeup`, `perfume`, `home`. Коды вопросов, вариантов и виджетов — [`content-map.md`](content-map.md).

У клиента одна строка `profiles`. `profile_revision` растёт при обновлении, вторая строка не создаётся.

## 9. Как результат попадает в ENSI

Очередь `ensi_outbox` пополняется в той же транзакции, что и запись профиля:

| Момент | Доставка |
|---|---|
| `POST /api/v1/me/session/base:complete` | да |
| `POST /api/v1/me/session/passport:complete` каждой категории | да, та же строка профиля |
| Завершение базы или категории после «Пройти заново» | да, та же строка |
| Отдельный `PUT` ответа | нет |
| `POST /api/v1/me/session:reset` | нет |
| Открытие и импорт из ENSI | нет, импорт помечается `sent` |

Воркер забирает `pending` и вызывает `upsertProfile` для того же `customer_id`. Тело — `toEnsiPayload`: фиксированные `attributes.beauty_*` (список в [`ENSI.md`](ENSI.md)) и вложенный `beauty_profile` со всеми полями раздела 8. Ключи черт: `beauty_trait_` + ключ `traits` с точкой, заменённой на `_`.

Второго канала нет. Webhook не реализован (возможный вариант позже, в коде его нет).

Pull, если системе нужен профиль без ожидания push:

`GET /api/v1/integration/customers/{customerId}/profile`

Заголовок `X-Api-Key`. В OpenAPI схема называется `X-Api-Key`, имя заголовка тоже `X-Api-Key`, значение — env `INTEGRATION_API_KEY`. Профиль в `data`, статус доставки в `meta.ensi.status`. Нет профиля — 404.

## 10. Статус доставки

Это статус отправки профиля красоты в ENSI, строка очереди `ensi_outbox`. Не статус HTTP-ответа и не доставка текстов опросника пользователю.

Значения: `none`, `pending`, `sending`, `sent`, `failed`, `superseded`, `dead`.

Где смотреть:

- `GET /api/v1/me/profile` — поле `data.ensi.status` (и `revision`, `lastAttemptAt`, `attempts`, `lastError`). Профиля может не быть: `data.profile = null`, HTTP 200, статус `none`.
- `GET /api/v1/integration/customers/{customerId}/profile` — поле `meta.ensi.status`. Нет профиля — 404.
- `/metrics`: `ensi_outbox_size`, `ensi_sent_total`, `ensi_failed_total`, `ensi_outbox_dead_total`.

`superseded` — прежняя недоставленная ревизия этого клиента, её заменила более новая. `dead` — исчерпаны повторы 5xx, 429 или сети. Прочий 4xx остаётся `failed` и сам в `dead` не переходит.

## 11. Имена в OpenAPI

Спецификация генерируется из схем маршрутов, отдельного yaml опросника в репозитории нет.

| Имя схемы | Заголовок | Смысл |
|---|---|---|
| `bearer` | `Authorization: Bearer` | JWT пользователя |
| `X-Api-Key` | `X-Api-Key` | сервисный ключ, env `INTEGRATION_API_KEY` |
| `X-Admin-Token` | `X-Admin-Token` | конструктор, env `ADMIN_TOKEN` |

Глобальная схема — `bearer`. Опубликованный `GET /survey` и служебные методы — без авторизации (`security: []`).

## 12. Что ещё не закрыто

- Ключ, `iss`, `aud` и имя клейма JWT передаёт команда ЛК.
- URL, метод, авторизация и идемпотентность приёма профиля передаёт команда ENSI. Пока `ENSI_SINK=file`.
- Webhook в ENSI не делаем, пока его явно не закажут.
