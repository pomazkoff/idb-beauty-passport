## 2. Сервис у нас или внешний?

Production опросника работает в инфраструктуре ИЛЬ ДЕ БОТЭ. Это API, воркер, PostgreSQL и конструктор из этого репозитория.

Репозиторий передаётся, когда аналитик принимает сервис.

| Что | Адрес |
|---|---|
| API | `https://beauty-api.iledebeaute.ru` |
| Статика эталона, если её поднимают | `https://beauty-quiz.iledebeaute.ru` |

ENSI остаётся внешней системой. Воркер отправляет ей новые ревизии профиля. При пустом входе залогиненного клиента API читает уже сохранённый профиль.

## 3. Когда будут web-компонент и репозиторий бэкенда?

Бэкенд уже в этом репозитории: `apps/api`, `apps/worker`, пакеты `packages/*`.

Интеграция этой задачи — нативные вызовы API фронтом ЛК, не встройка web-компонента. Фронт ЛК сам рисует вопросы и ходит в методы из [`INTEGRATION.md`](INTEGRATION.md). Компонент `<idb-beauty-quiz>` (`apps/web`, сборка `dist/embed/`) остаётся необязательным эталоном тех же вызовов. Публикации в npm нет.

## Комментарии к документу от 2026-10-06

1. В этой задаче web-компонент не встраиваем. Интеграция — нативный API.
2. Без токена сервис пользователя не пускает. Принимаются только токены авторизации пользователей ИЛЬ ДЕ БОТЭ.
3. Токен проверяется: подпись RS256, `iss`, `aud`, срок, id клиента из клейма. Этот id равен id клиента в ENSI.
4. `GET /api/v1/me/session` для фронта ЛК требует только JWT пользователя. `X-Admin-Token` нужен, только если конструктор передал query `version`.
5. В OpenAPI ключ чтения называется `X-Api-Key`: и имя схемы, и имя заголовка. Значение — env `INTEGRATION_API_KEY`.
6. Роли «Эксплуатация» нет. `health`, `ready` и `metrics` — служебные методы без роли.
7. Результат уходит воркером в ENSI после завершения базы, после каждой завершённой категории и после завершения, которое следует за «Пройти заново». Плюс pull `GET /api/v1/integration/customers/{customerId}/profile`. Webhook не реализован.
8. Объект `answers` описан: у каждого `question_key` поля `optionCodes`, `skipped`, `timeMs`, `answeredAt`.
9. Статус доставки — это статус отправки профиля красоты в ENSI (`data.ensi.status` или `meta.ensi.status`), не доставка контента опросника пользователю.

## Решения владельца

1. Production — инфраструктура ИЛЬ ДЕ БОТЭ. Передача репозитория — когда аналитик принимает сервис.
2. API: `https://beauty-api.iledebeaute.ru`. Статика эталона: `https://beauty-quiz.iledebeaute.ru`.
3. JWT выпускает backend личного кабинета. Сервис опросника только проверяет его. Подтверждено: id клиента в JWT равен id клиента в ENSI. Ключ, `iss`, `aud` и имя клейма передаёт команда ЛК — [`INTEGRATION.md`](INTEGRATION.md).
4. Контракт приёма профиля принадлежит ENSI. Это зависимость: URL, метод, авторизация, идемпотентность. Пока контракт не передан, `ENSI_SINK=file`.
5. При открытии опросника для залогиненного клиента сервис читает профиль из ENSI и показывает уже собранный результат. Если ENSI недоступен или в file-sink нет файла, опросник открывается с начала. «Пройти заново» профиль заново не подмешивает.
6. Профиль красоты один на клиента и хранится постоянно. Повторное прохождение и добавление категории обновляют эту запись в базе и в ENSI (upsert), а не создают второй профиль. `profile_revision` при этом растёт.
7. Интеграция ЛК — нативный API. Фронт ЛК рисует опросник сам. Web-компонент не является контрактом этой задачи.

## Что ещё нужно получить

Это входные данные команд, не выбор варианта размещения.

1. От ЛК: `JWT_JWKS_URL` или PEM публичного ключа, `iss`, `aud`, имя клейма с id клиента (если это не `sub`), origin страницы, с которой фронт вызывает API.
2. От ENSI: контракт приёма профиля (URL, метод, авторизация, идемпотентность) и ответ `GET` по `ENSI_FETCH_PATH`. Список — в [`ENSI.md`](ENSI.md).
3. Webhook в ENSI не делаем, пока его явно не закажут. Сейчас результат уходит push воркера и доступен pull-методом.
